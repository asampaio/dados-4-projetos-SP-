# [USBD04] Relational Model (Logical Level)

* **Priority:** High
* **Story Points:** 5
* **Module / Component:** `Database` / `Relational Model (Logical Level)`
* **Status:** Draft

---

## 👤 User Story Description

**As a** Product Owner, **I want** the relational model to be created (logical level), **so that** the data model covers all the requirements of the project and the physical model script for Oracle RDBMS can be automatically generated by a specific tool or an LLM.

## 💬 Customer Specifications & Clarifications

* **Clarification:** The model must cover the requirements presented in the project document, as well as any additional requirements resulting from the provided user stories (e.g., [USEI01] to [USEI05]) and from the feedback/clarifications provided by the client.
* **Clarification:** The model is delivered at the **logical level** (entities, attributes, data types, keys, relationships, cardinalities and constraints), independent of physical tuning aspects.
* **Clarification:** The target RDBMS is **Oracle**; the logical model must contain enough detail to allow the physical script to be generated automatically.
* **Assumption (to confirm with the customer):** Data types are expressed with Oracle-compatible types (`VARCHAR2`, `NUMBER`, `DATE`/`TIMESTAMP`, ...).
* **Out of Scope:** Creating the tables in Oracle, populating them with data and the Oracle FreeSQL demonstration (see [USBD05]); physical tuning (indexes, partitions, tablespaces); application code.

---

## ✅ Acceptance Criteria

* [ ] **AC1 - Requirements Coverage:** The data model covers the requirements presented in the project document, as well as any additional requirements resulting from the provided user stories and the feedback/clarifications provided by the client.
* [ ] **AC2 - Complete Model:** A complete model is delivered, including:
  * an **ER diagram** (entities, attributes, relationships, cardinalities);
  * all **constraints** (primary keys, foreign keys, unique, not null, check, default values).
* [ ] **AC3 - Script Generation:** The model is detailed enough to allow the **physical model script for Oracle RDBMS** to be automatically generated by a specific tool or an LLM.

---

## 🔒 Non-Functional Requirements & Security

* **Integrity (NFR1):** Referential integrity and business rules are enforced through constraints (PK, FK, UNIQUE, NOT NULL, CHECK).
* **Normalization (NFR2):** The model should be normalized (at least 3NF), avoiding redundancy; any denormalization must be justified.
* **Integration (NFR3):** The model must support the Java application; other components are integrated through files, program arguments or environment variables.
* **Documentation (NFR4):** Diagrams in SVG style figures; consistent naming conventions across all tables, columns and constraints.
* **Maintainability:** The model must be easy to maintain and extend with new functionalities.

## Edge Cases

* **Missing Requirement:** A requirement present in a user story but not in the model must be flagged and added.
* **Many-to-Many Relationships:** Resolved through associative (junction) tables with composite keys.
* **Optional Relationships:** Nullable foreign keys must be explicitly documented.
* **Reused Entities:** Entities shared by several user stories (e.g., orders, customers, robots) must be modelled only once.
* **Status Values:** Enumerated values (e.g., robot status `BUSY`) are enforced with CHECK constraints or lookup tables.
